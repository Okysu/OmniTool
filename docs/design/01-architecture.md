# 架构设计：OmniTool

> 面向：参与本项目开发的工程师。阅读前不需要了解本仓库，但假定你熟悉 Vue 3 与浏览器平台 API。

## 1. 一句话概括

OmniTool 是一个**插件即一切**的本地优先工具箱：宿主只提供沙盒、文件系统、任务调度与 UI，
**所有工具能力——包括内置的 PDF 与图片工具——都以插件形式运行在不透明来源（opaque origin）的沙盒里**。

这条约束是刻意的。如果一个内置工具无法只用公开的 Plugin API 写出来，那说明 API 缺了东西，
问题会在第一时间暴露，而不是等到第三方开发者来踩。

## 3. 沙盒：为什么是这个方案

### 3.1 选型

| 方案 | 隔离强度 | 不阻塞 UI | 复杂度 | 结论 |
| --- | --- | --- | --- | --- |
| 同源 Worker | ✗ 可直接读 IndexedDB / OPFS / 带 Cookie 的 fetch | ✓ | 低 | 否决：不是安全边界 |
| 不透明源 iframe | ✓ | ✓（宿主 UI），✗（插件自身 RPC 会卡） | 中 | 作为降级层保留 |
| **不透明源 iframe + 内嵌 Worker** | ✓ | ✓ | 中高 | **采用** |
| QuickJS-WASM | ✓✓ 可做 CPU 配额 | ✓ | 高 | 否决：JS 慢 10–50 倍，不适合密集计算 |

### 3.2 四层围栏

从外到内，每一层独立生效：

1. **`sandbox="allow-scripts"`，且不加 `allow-same-origin`。**
   这是整套方案的基石：iframe 获得不透明来源，因而**没有任何**同源存储——
   `document.cookie`、`localStorage`、`indexedDB`、OPFS 全部不可达，也拿不到宿主 DOM。
   端到端测试中的 `idb:BLOCKED` 就是对这一层的直接验证。

2. **frame CSP：`default-src 'none'; connect-src 'none'`。**
   插件无法发起任何网络请求、加载任何子资源、嵌套任何 frame。
   `host.net.fetch` 是唯一出口，而它需要用户授权。
   `'unsafe-eval'` 是必须的（执行插件源码正是目的），但它不提供额外权力——
   eval 出来的代码继承的是同一套（空的）权限。

3. **能力授权**，在 `capabilities/index.ts` 中对**每一次**调用检查。
   用户在安装时逐项勾选；未勾选的能力，对应 `host.*` 调用在宿主侧被拒绝，
   插件的其他工具照常可用。

4. **文件收敛**：插件只能读取*当前正在运行的调用*的输入文件，以及*它自己创建*的输出文件。
   既不是"整个工作区"，也不是"所有历史文件"。

### 3.3 降级：iframe-worker → iframe

在不透明来源里用 blob URL 起 Worker 在规范上是合法的，但各引擎历史实现参差。
frame 引导程序会先尝试 Worker 并等待一次握手（2s 超时），失败则就地在 iframe 主线程运行同一份 runtime。

**两层的来源隔离完全相同，差别只在线程。** 实际生效的层级会上报给宿主
（`sandboxState.isolation`），并直接显示在首页徽标与设置的诊断面板里——
安全属性不该靠猜。

Chromium 实测：`iframe-worker`。

## 4. 文件契约：句柄式 VFS

插件**从不持有文件字节**。它拿到的是 `FileRef`（不透明 id + name/size/type），
按需通过 `host.fs.read(id, offset, length)` 取字节范围。

这样做换来三件事：

- **2GB 视频不会被跨沙盒边界克隆。** 字节始终留在宿主的 OPFS 里。
- **权限天然可控。** "能读哪些文件"退化成一次 Set 查表，而不是"传了什么就能看什么"。
- **可流式处理。** 输出走 create → write* → close，边算边落盘。

存储分两级，启动时探测一次：

1. **OPFS** —— 字节落盘、刷新不丢、不占堆内存。
2. **内存** —— OPFS 或主线程写入流不可用时（Safari 主线程、隐私窗口）的兜底。

探测是**功能探测**而非 UA 嗅探：实际去 `createWritable()` 写一个字节。
降级原因会明确写进诊断面板，不静默劣化。

## 5. 依赖注入

沙盒 `connect-src 'none'`，所以插件自己加载不了任何库。
插件在清单里声明 `deps`，**宿主**负责拉取、校验 SRI、缓存进 IndexedDB，再把源码文本注入沙盒。

这把"依赖加载"从一个隐形的运行时副作用，变成了一个可审查、可缓存、可离线的显式步骤：

- 安装审查弹窗会列出每个依赖的 URL，并说明它们将获得与插件相同的权限。
- 声明了 `integrity` 的依赖，**每次加载都校验**，缓存命中也不例外。
- 内置 PDF 插件指向同源的 `/vendor/pdf-lib.js` 与 `/vendor/pdfjs.js`，因此整个应用可完全离线运行。
- ESM-only 的 npm 包由 `scripts/vendor.mjs` 用 esbuild 打成 IIFE 后才能注入（注入方式是求值经典脚本）。

## 6. 订阅更新策略

这是安全上最容易出事的地方，规则只有两条：

- 能力集**未变**的更新 → 静默应用，沿用用户已给的授权。
- 申请了**新能力**的更新 → 扣下不装，进入待审查队列。

**订阅永远无法自我提权。** 一个今天只读文件的插件，不可能在明天的更新里悄悄拿到网络权限。

## 7. 并发与 UI 响应

- 每个插件一个沙盒实例，首次调用时惰性启动，之后复用（省掉约 50ms 的 frame + 依赖开销）。
- 全局并发上限可配（默认 2），音视频转码这类重负载建议保持低值。
- 进度回传在插件侧节流到约 20 条/秒，防止 tight loop 刷爆宿主。
- 端到端实测：512×512 PNG 压缩期间，主线程到下一帧 9–12ms。

## 8. 刻意没做的事

- **没有 Pinia。** 状态就是几个 `reactive` 模块，跨组件共享靠直接 import。少一层封装。
- ~~没有 UI 组件库~~（第 2 轮起改用 shadcn-vue CLI 官方组件，见 `docs/iterations/02-summary.md`）。
- **没有压缩的 ZIP。** 批量结果本就是已压缩的媒体，STORE 模式省掉一个依赖。
- **插件不能写 DOM。** 插件只能*描述*界面（表单或 v2 的组件树），由宿主用 shadcn 组件渲染；
  需要像素级交互时，宿主把一块 `OffscreenCanvas` 转交进沙盒。插件注入不了标记、样式或事件处理器。

## 9. 已知边界

- 同一插件的多个并发调用共享一个 `allowedInputs` 集合，因此 A 调用理论上可读到 B 调用的输入。
  这是**插件内部**的边界模糊，跨插件与对宿主的边界不受影响。若要收紧，需要把调用 id 透传进
  `host.fs.*`（见 `docs/design/02-plugin-api.md` 的"未来变更"）。
- 移动端（<768px）侧边栏收进抽屉，顶栏搜索与图标按钮折叠为图标与溢出菜单。
- ~~`ffmpeg.*` 留到第 2 轮~~（已实现，见下节）。

## 10. 第 2 轮新增

```
宿主能力层（主线程 / 专用 Worker）
  capabilities/vault.ts   kv 加密存储 + 封存式凭据（域名绑定、只可引用不可读取）
  capabilities/ffmpeg.ts  FFmpeg.wasm：占位符挂载、图像序列、串行队列、线程预算
  capabilities/onnx.ts    ONNX Runtime Web：下载确认、SHA-256 校验、OPFS 缓存、专用 Worker 推理（第 3 轮重写，见 11.3）

界面协议（宿主 ⇄ 沙盒）
  ui-open / ui-render / ui-state / ui-event / ui-canvas / ui-close
  插件描述组件树 → core/ui/schema.ts 清洗 → components/panel/ 用 shadcn 渲染
  canvas 节点：transferControlToOffscreen() 后跨 host→frame→worker 两跳转交
```

几条值得记住的约束，都是在实现中踩出来的：

- **沙盒里没有 `crypto.subtle`**：不透明来源不是安全上下文。需要摘要时走 `host.fs.digest`。
- **沙盒主层级是 Worker**：没有 `DOMParser`、没有 `document`。编辑器的类型库因此用 `webworker` 而非 `dom`。
- **`call` 消息带调用 id**：宿主侧耗时操作（转码、模型下载）的进度与取消能准确归属到任务行；
  也为把文件可见范围从插件级收紧到调用级铺好了路。
- **FFmpeg 线程必须由宿主统一预算**：多线程核心的 pthread 池固定 32，按核数开线程会在多核机器上永久死锁。
- **任务队列是布局的一部分而不是浮层**：浮层与 sticky 面板的遮挡无法靠尺寸调整彻底消除。

## 11. 第 3 轮新增

### 11.1 图片双引擎

```
                      ┌─ Canvas（默认）：快、GPU 加速；按 EXIF 摆正并去除元数据
图片工具 ── 选择引擎 ──┤
                      └─ ImageMagick（wasm，按需加载 14 MB）：
                           · 动图（GIF / 动态 WebP）逐帧处理
                           · 保留 EXIF 与 ICC
                           · 解码 HEIC / TIFF / PSD / JXL / RAW，编码 GIF / TIFF / JXL
```

引擎按文件选择，而不是按工具：几何类工具（转换、缩放、裁剪、旋转）在「动图输出为动图格式」「浏览器解不了 / 编不了」「要求保留元数据」
时整体切到 magick；其余工具保持 Canvas 实现，只在 `decode` / `encode` 里用 magick 兜底编解码。
单帧工具遇到动图时会明确提示「只保留第一帧」，而不是悄悄压平。

magick 跑在**插件沙盒自己的 Worker 里**，没有新增任何宿主能力。为此依赖机制扩展了两点（均为非破坏性新增）：

- `lazy` 依赖：只在插件调用 `loadDependency(id)` 时由宿主拉取，14 MB 的模块不拖慢每次沙盒启动；
- `assets`：宿主拉取并校验二进制资源，以 ArrayBuffer 转交进沙盒（沙盒自身没有网络）。

**安全边界不变**：可加载的依赖列表取自**安装记录**（用户审查过的清单），不是沙盒启动时自报的清单——
插件代码先于自报清单执行，若以自报清单为准，`loadDependency` 就会变成绕过 `net` 能力的任意读取通道。

### 11.2 依赖注入的一个陷阱

注入方式是间接 `eval`。esbuild 会把源码中的 `"use strict"` 提升到产物开头，而**严格模式下 eval 代码的顶层 `var` 不会成为全局变量**——
依赖「加载成功」，全局却不存在。vendor 脚本为每个 IIFE 产物追加 `globalThis.X = X`，
运行时对声明了 `global` 却没定义它的依赖直接报出原因；单元测试的插件运行器也改为间接 `eval`，与沙盒完全一致。

### 11.3 ONNX 推理 Worker

```
主线程                                   onnx.worker（独立 chunk，仅含 ORT）
  确认弹窗 → 下载 → SHA-256 → OPFS 缓存 ──字节（转移）──▶ InferenceSession.create
  plugin run ─────────── feeds（转移）──────────────────▶ session.run
             ◀─────────── outputs（转移）───────────────┘
                                             └─ pthread workers（em-pthread，从 /vendor/ort/*.mjs 启动）
```

最初使用 ORT 自带的 `env.wasm.proxy`。它从 ORT 自身的脚本地址启动代理 Worker，而 Vite 把 ORT 内联进了应用主 chunk——
代理 Worker 于是加载了**整个应用**，在 `document` 上崩溃，随后 WebGPU 初始化失败、wasm 回退又撞上「重复初始化」。
改为自有 Worker 后：模型下载、确认与校验仍在主线程（需要用户与网络），会话创建与推理全部在 Worker；
只在检测到真实 WebGPU 适配器时才请求 WebGPU（让 ORT「试一下再失败」会污染它的 wasm 初始化）。

### 11.4 其他结构调整

- **VFS 文件名允许相对路径**：逐段清洗，不能以 `..` 或绝对路径逃出；解压、按文件夹导出附件后，「打包下载 ZIP」保留目录结构。存储始终以 id 为键。
- **pdf.js 画布工厂**：pdf.js 在沙盒 Worker 里默认用 `document.createElement('canvas')` 解码图片，含图片的页面全部失败
  （纯文字页面从不需要，此前测试素材恰好都是纯文字）。PDF 与 AI 插件改为注入基于 `OffscreenCanvas` 的工厂。
- **插件面板状态**：`PluginPanel` 维护一份同步更新的工作副本。`v-model` 在父组件重新渲染前读回的是旧值，
  同一 tick 内的两次变更（组件回报媒体信息后立即回报选区）会让后一次覆盖前一次。
- **界面节点 `media` / `reorder`**：宿主负责播放、拖拽、预览，插件只读写状态键，见 `02-plugin-api.md`。


## 12. 第 4 轮新增

### 12.1 FFmpeg 线程预算：静态图输入固定单线程

给视频叠加图片水印（`scale2ref` + `overlay`）在多线程内核上会**永久挂起**，单线程内核正常。
逐项排除后定位到：静态图片输入被帧级多线程解码，与 `scale2ref` 的帧请求时序互相等待。
修复在宿主的线程预算里（`applyThreadBudget`）：所有静态图片输入固定 `-threads 1`，视频输入不受影响；
同时按真实扩展名挂载输入文件（不再统一叫 `input`），让 FFmpeg 按正确的解复用器处理图片。
这是根因修复，没有提供「关闭多线程」之类的开关。

### 12.2 共享的中文字体资源

烧录字幕、视频文字水印、表情包、Markdown 转 PDF、PDF 盖章与表单、可搜索 PDF 都需要中文字形。
Noto Sans SC Regular（OFL-1.1，约 10 MB）不进仓库：构建时按固定 SHA-256 下载并缓存，作为**按需依赖的二进制资源**下发给需要它的插件。
PDF 类输出通过 fontkit 只嵌入用到的字形（通常几 KB）；FFmpeg 通过 `fontsdir` 使用；Canvas 通过 Worker 内的 `FontFace` 使用。
离线且没有缓存时构建照常成功，相关工具会明确报告字体缺失。

### 12.3 把 Emscripten 模块放进沙盒

qpdf（PDF 加密、线性化、校验）与 libarchive（7z / RAR）都是 Emscripten 产物，进入「无网络」沙盒要解决三件事：

| 问题 | 处理 |
| --- | --- |
| 胶水代码里有 Node 分支（`require('fs')`） | vendor 打包时这些模块保持 external，并把 `process.versions` 定义为空对象，锁定浏览器分支 |
| libarchive 支持 `wasmBinary` | 直接传入作为依赖资源下发的 wasm 字节 |
| qpdf 这个构建**不支持** `wasmBinary`，总是 `fetch('qpdf.wasm')`，而沙盒里的 `fetch` 是只读的禁用桩 | 打包时用 esbuild `define` 把 qpdf 胶水里的 `fetch` 标识符改写成模块内函数 `qpdfInlineFetch`，它只会返回插件拿到的 wasm 字节；全局 `fetch` 仍然锁死，产物里不存在任何真正的网络调用 |

另一个限制：该 qpdf 构建关闭了 C++ 异常捕获，qpdf 自身「文件损坏 → 重建交叉引用表」的恢复逻辑依赖异常，因此无法工作
（实测：错误的 `startxref`、错误的对象偏移都直接失败，而原生 qpdf 能修复）。
`repair` 因此改用 pdf-lib 的容错解析（按对象顺序扫描、不依赖交叉引用表）重建文件，再用 qpdf `--check` 校验结果。
同一原因还影响 `--is-encrypted` / `--requires-password` 对需要密码文件的退出码，插件改为结合输出文本判断。

### 12.4 ONNX 保留张量

```
沙盒插件                     宿主主线程                        onnx.worker
run(feeds, {keep})  ──▶  句柄表 t17 → {pluginId, 42}  ──▶  kept.set(42, ortTensor)
     ◀── { type, dims, tensor: 't17' } ──                  （数据不离开 Worker）
run({ past: {tensor:'t17'} }) ─▶ 校验归属 → {tensor: 42} ─▶ kept.get(42) 直接作为输入
dispose(['t17'])  ─────────▶  删除映射  ─────────────────▶  tensor.dispose()
```

Whisper 解码每个 token 都要喂回 KV 缓存（base 模型交叉注意力缓存约 37 MB）。保留张量后，每步跨线程的只剩 logits（约 200 KB）。
句柄与会话同样按插件隔离、有数量上限、随沙盒回收释放；`outputs` 选项让缓存分支不再计算和回传「原样透传」的交叉注意力输出。
实测 11 秒语音在 Node 中端到端 1.4 秒，句柄零泄漏。

### 12.5 画布的重新挂载

`canvas` 节点的 `OffscreenCanvas` 只能转交一次。节点被 `when` 隐藏再显示时，宿主挂载的是新元素、转交的是新画布，
插件手里的旧画布画了也看不见（签名板切到「文字」再切回来就是空白）。运行时新增 `ui.on('canvas')` 事件，
每次转交都通知插件重画。

## 13. 工作流（自动化流水线）

「把多个工具串起来」是平台功能，不是一个工具：

```
拖入文件 ─▶ 步骤 1（工具 A）─▶ 输出 ─▶ 按 accept 过滤 ─▶ 步骤 2（工具 B）─▶ … ─▶ 最终结果
                 │                                          │
                 └──────── 每次调用都是任务队列里的普通任务 ────────┘
```

- **不需要插件适配**。每一步就是一次普通的 `run(ctx)`，走同一个沙盒、同一个任务队列（受并发上限约束，出现在任务坞里）。
- **只有表单工具可以作为步骤**。带 `setup(ui)` 的工具，参数来自交互（裁剪框、签名、涂抹），流水线无法提供，选择器里直接不列出，运行前也会校验。
- **单文件工具自动扇出**：上一步产生多个文件、而下一步工具不接受多文件时，每个文件一个任务。
- **按 `accept` 过滤并如实报告**：不被接受的文件跳过并在步骤上注明；一个都不接受时以步骤名报错，而不是把错误的文件塞给工具。
- **中间文件**默认在整条流水线成功后删除，原始输入与最终结果永远保留；失败时保留，便于排查。
- 流水线以工具键（`插件 id/工具 id`）引用工具，保存在 `localStorage`；插件卸载后步骤显示为「找不到工具」，不影响其它流水线。导入的 JSON 按不可信数据逐字段清洗。
- 运行器（`src/core/pipelines/runner.ts`）不依赖队列与 VFS，依赖以参数注入，单元测试直接覆盖扇出、过滤、失败传播、取消与清理。

## 15. 第 6 轮新增

### 15.1 仓库内维护、按需订阅的扩展

```
extensions/
├─ index.json        订阅索引（url 相对索引文件）
├─ ai-toolkit.js     AI 扩展工具箱：一个插件，21 个工具
└─ README.md         订阅地址、服务商配置、本机模型的跨域设置
        │
        │  jsDelivr（https://cdn.jsdelivr.net/gh/Okysu/OmniTool@<ref>/extensions/index.json）
        ▼
插件与订阅 → 远程订阅 → 审查授权 → 与第三方插件完全相同的沙盒与能力仲裁
```

- **为什么不内置**：内置工具的承诺是「数据不出本机、默认无外联」。AI 扩展必须把文件内容发往模型服务，所以不进构建产物，只以订阅的形式提供，由用户在审查对话框里逐项授权。
- **没有特权**：扩展只用公开的 Plugin API（`net`、`secret`、`kv`、`fs`、`ui`、`ffmpeg`）与同源 `/vendor` 依赖（`data-libs`、`pdfjs`），与任何第三方订阅走同一条路径；订阅更新想要新能力时照常被扣下审查。
- **一个插件而不是多个**：连接设置（`kv`）与 API Key（`secret`）都按插件 id 隔离。拆成多个插件会让用户为每个工具重复配置、重复录入 Key。
- **凭据**：Key 通过 `host.secret.request('apiKey', { origins: [接口 origin] })` 录入，请求头写 `Authorization: Bearer {{secret:apiKey}}`，由宿主替换。更换接口地址后 origin 不再匹配，工具会用 `force` 重新请求录入，而不是让请求在宿主处失败。`secret` 是中风险能力、默认不勾选；未授权时面板与运行给出可操作的提示，只用本机免 Key 服务的用户可以不授权。
- **本机模型**：Ollama / LM Studio 在 localhost 上，默认被 `host.net` 的内网拦截挡住，需要用户在「设置 → 安全」中放行；模型服务本身还需允许跨域。两处都写进了扩展 README，并在错误信息里提示。
- **服务商差异在插件内消化**：不支持 JSON 模式的服务对 `response_format` 返回 4xx 时去掉该字段重试；429 / 5xx 按 `Retry-After` 退避；推理模型内联的 `<think>` 块被剥离；模型把答案包在代码块或说明文字里时，从中提取第一个完整 JSON 值。宿主拦截与凭据错误不重试。
- **视觉目标检测的坐标**：提示词要求 0–1000 归一化的 `[x1, y1, x2, y2]`，解析端兼容 Gemini 的 `box_2d`（yxyx）、0–1 小数、以及 Qwen2.5-VL 的绝对像素（相对于**发送给模型的缩放图**）。所有框先落到 0–1，再换算为 YOLO（归一化）、COCO 与 LabelMe（原图像素）。

### 15.2 凭据使用提示合并

`host.net.fetch` 每次替换凭据都会提示发往的域名。批量 AI 任务一次会发出几十上百个请求，逐条提示会刷屏并挤掉真正的错误提示。
现在同一插件、同一 origin、同一组凭据在 15 秒内的请求合并为一条提示，并更新计数（「已向 … 发送 N 次请求并使用凭据」）。
每次使用仍然会被提示与记账（`lastUsedAt`、`useCount`），变化的只是展示方式；`pushToast` 为此增加了可选的 `id`，用于原地更新同一条提示。

### 15.3 插件记录未持久化（修复）

「插件与订阅」页的审查对话框把待安装的插件放在 Vue 的 `ref` 里，`commitInstall` 拿到的是深层响应式代理。IndexedDB 无法结构化克隆代理，
`persist()` 又把异常吞掉了：**通过导入或订阅安装的插件在刷新后消失**，下次订阅同步时又作为「新插件」弹出审查。

修复分两处：`commitInstall` 先 `toRaw`；`persist()` 写入与响应式系统完全脱钩的 JSON 快照（记录本来就是纯 JSON 数据），并且保存失败时明确提示，不再静默。
内置插件每次启动从包内重新登记，因此一直没有暴露这个问题；新增的 extensions 端到端套件在刷新后继续使用已订阅插件，覆盖了这条路径。

### 15.4 安装前风险报告的两处误报

- 「直接网络调用（将被拦截）」的规则 `\bfetch\s*\(` 也匹配 `host.net.fetch(`，所有正确使用宿主代理的插件都会被误报。规则改为只匹配不跟在 `.` 后的裸调用。
- 能力使用检测没有 `secret` 与 `onnx`，报告会把它们列为「声明了但未使用」。已补上（`{{secret:` 占位符也算使用）。

两处都只影响审查对话框的说明文字，默认勾选策略不变：`secret`（中风险）仍需用户手动开启。

### 15.5 工作流：资料库、全屏编辑器与置顶运行页

| 路由 | 页面 | 布局 |
| --- | --- | --- |
| `/flows` | 资料库：「我的工作流」卡片（步骤图标链、置顶、运行、编辑、删除）；「新建工作流」对话框填写名称并选择空白或模板 | 应用布局 |
| `/flows/:id/edit` | 编辑器：页眉（名称、列表 / 流程图、置顶、运行页、导出、删除）、步骤区、右侧运行栏 | 独立全屏（`meta.layout: 'standalone'`），与插件教程一致 |
| `/flows/:id` | 运行页：像工具页一样提供输入、运行与结果，右侧列出步骤及改动过的参数 | 应用布局 |

- **置顶与工具共用一个列表**。`settings.pinned` 里工具的键是 `pluginId/toolId`，工作流是 `flow:<id>`（工具键不可能以 `flow:` 开头），因此侧边栏与命令面板中二者可以混合排序。删除工作流会同时取消置顶。侧边栏的拖动排序改为按键移动：此前按「显示出来的列表」的下标去改 `settings.pinned`，一旦有失效的置顶项（插件已卸载）就会移动错误的条目。
- **运行状态属于工作流，不属于页面**。输入文件、输入文本与当前运行记在按工作流 id 保存的会话里（`pipelineSession`），编辑器的运行栏与运行页是同一个组件 `PipelineRunPanel`，在两页之间切换不会丢失输入或正在进行的运行。会话只在本次打开应用期间存在。
- **文本输入**。首个步骤的工具声明 `input: 'text' | 'both'` 时，运行栏提供「直接输入」，文本按该工具的 `textFileName` 写成工作区文件，与工具页的处理完全一致。
- 编辑器是全屏页面，不显示任务队列浮窗；运行进度在运行栏内逐步显示。

### 15.6 流程图节点自由摆放

- `Pipeline.layout` 保存用户拖动过的节点位置，键为步骤 id 或 `input` / `output`；没有记录的节点使用从左到右的自动位置。
- 拖动结束时把**所有**节点的当前位置写入 `layout`：只记被拖的那个，之后增删步骤时其余自动节点会整体移位，与手工摆放的节点重叠。在已手工摆放的图中插入步骤时，新节点放在所插入连线两端节点的中点下方。
- 拖动过程中只更新本地的临时位置，松开时才写回工作流，避免每一帧都触发 localStorage 持久化；位置按 12 px 网格吸附，与画布点阵一致。拖动之后紧随的 `click` 被忽略，不会误触发选中。
- 连线根据两节点的相对位置选择出入边：上下排列时从底边连到顶边，左右排列时从右边连到左边（反向时左连右），控制点沿出入方向延伸，距离随节点间距变化。
- 「自动排列」清空 `layout`。导入与导出保留位置；导入时步骤获得新 id，位置随之迁移。不可信文件中的坐标只接受数值且绝对值不超过 100 000，未知的键被丢弃。
- 滚轮平移改为二维（Shift + 滚轮横向）。原先纵向滚轮被映射为横向，是单行布局时的取舍；节点可以上下摆放后不再合适。
- 全屏编辑器里流程图占满高度，参数检查器只在选中步骤时浮在画布右侧（Esc 或关闭按钮收起），画布宽度不被常驻的空检查器占用。

### 15.7 对话框宽度（修复）

shadcn-vue 的 `DialogContent` / `DialogScrollContent` 是只有一列的 CSS 网格。隐式列宽为 `auto`，会被 `truncate`（不换行）文字的最小内容宽度撑开，
于是订阅安装审查里较长的工具描述与来源地址把卡片推出了对话框。两处组件加上 `grid-cols-[minmax(0,1fr)]`，列宽始终等于对话框宽度，
截断与换行按预期生效；滚动版对话框同时补上手机屏幕的左右留白。按贡献约定在文件头标注了 `LOCAL MODIFICATION`。
